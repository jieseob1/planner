# 주간·월간 AI 회고 보고서 — 구현 명세

상태: 2026-09-07 요구사항 및 설계. **아직 AI API 연결·보고서 생성·자동 발행을 구현하거나 실행하지 않았다.** 기존 기간별 목표·회고 로컬 구현과 구분한다. AI 제공자·예산과 자동 생성 여부는 사용자 답변 대기 중이다.

## 사용자에게 제공할 경험

`돌아보기 → 주/월 선택 → AI 보고서 → 근거 확인 → 다음 기간 계획`

- 직접 쓰는 회고와 AI 보고서는 별개로 보관한다. AI가 사용자의 글을 덮어쓰거나 목표·할 일·일정을 자동 수정하지 않는다.
- 주간 보고서는 날짜별 실행을, 월간 보고서는 해당 월에 포함되는 주별 흐름을 정리한다. 월 경계의 주는 그 달에 속한 날짜만 집계한다.
- 목표나 타이머가 없어도 이용할 수 있다. 계획 시간, 기록 시간, 완료한 일, 목표 측정값을 각각 표시하고 임의의 종합 점수로 합치지 않는다.
- 생성한 보고서는 앱 안에서 기간별 목록으로 다시 연다. 최초 범위에 이메일/PDF 발송, 외부 공개 링크는 포함하지 않는다.
- `다시 생성`은 새 버전을 만든다. 이전 결과와 그때 사용한 근거는 남긴다. 생성 시점보다 나중에 수정한 데이터가 옛 보고서에 자동 반영되는 것처럼 보이지 않게 한다.
- 분기·연간 확장은 같은 구조를 재사용하되, 첫 구현과 검증 범위는 주간·월간으로 한다.

## 보고서 구성

| 구역 | 내용 | 근거가 부족할 때 |
| --- | --- | --- |
| 한눈에 보기 | 기간, 데이터 기준 시각, 완료 개수·계획 시간·기록 시간, 핵심 요약 | 무엇이 기록되지 않았는지 표시 |
| 이번 기간에 한 일 | 날짜별/주별 실제 저장된 완료 항목과 실행 기록 | 날짜 없는 과거 완료 항목은 날짜를 추정하지 않음 |
| 잘된 점 | 반복해서 실행한 행동, 직접 작성한 긍정적 회고 | 기록이 뒷받침하지 않으면 판단 보류 |
| 막힌 점 | 저장된 미완료 일정과 사용자가 적은 방해 요인 | 미완료 이유·감정·건강·생산성을 단정하지 않음 |
| 목표 점검 | 기간에 해당하는 목표와 측정 시점 | 현재값을 과거 기간 말의 값으로 소개하지 않음 |
| 다음 기간 제안 | 근거가 있는 작은 조정 1~3개와 확인 질문 | 성격 평가나 과도한 목표 제안 금지 |

사실 요약과 AI의 해석·제안을 시각적으로 구분한다. 각 관찰에는 근거 항목을 붙인다. 기간 비교는 같은 집계 규칙을 사용하며, 이전 기간에 기록이 없으면 감소율을 계산하지 않는다. 월간 보고서는 주간 AI 결과를 그대로 재요약하지 않고 원본 저장 기록을 바탕으로 작성한다.

## 입력 데이터와 데이터 부족 정책

- JWT로 확인한 본인 계정의 **서버에 저장된** 활성 계획 및 종료·보관 계획, 기간별 목표·회고만 읽는다. 미저장 초안이나 충돌 중인 기기 데이터를 자동 전송하지 않는다.
- 기존 `summarizePeriod` 정책과 일치하게 안정적 항목 ID로 중복을 제거하고, 현재 계획을 우선한다. 계획 시간은 날짜별 구간 합집합으로 계산한다.
- 외부 캘린더의 제목·참석자, 계정 이메일·인증 토큰·연동 비밀값은 전송하지 않는다. 할 일/목표의 자유 메모는 기본 제외하고, 회고 본문은 별도 동의한 분석 범위로 취급한다.
- TimeEntry는 observedAt 기준의 기록 시간이다. 실제 시작/종료 구간이나 자정 너머 실행을 재구성하지 않는다.
- 목표 변화는 비교 가능한 시점의 측정 기록이 있을 때만 서술한다. 현재 목표값과 과거 회고의 최초 checkpoint는 측정 시점이 다를 수 있다.
- 숫자 집계는 서버의 결정적 코드가 수행한다. LLM에 계산을 맡기지 않는다. 입력 크기를 제한할 때 누락 범위를 명시하고 전체 기록을 분석했다고 주장하지 않는다.
- 실행/회고 근거가 전혀 없으면 유료 호출 없이 `보고서를 만들 기록이 아직 없어요`를 반환한다. 템플릿 문장을 AI 결과로 위장하지 않는다.

## 생성과 운영 구조

`사용자 요청 또는 동의된 주기 → 서버 근거 스냅샷 → MySQL 생성 작업 → Spring worker → AI 제공자 → 결과 검증·영속 저장 → 앱에서 조회`

1. 보고서 ID를 AI 호출 전에 발급하고 계정·기간·입력 해시·프롬프트 버전·모델과 함께 저장한다.
2. 본문, 근거 참조, 생성 상태, 생성 시각, 실제 사용 토큰, 비용 계산 근거를 저장한다. 가격 미설정/사용량 미수신은 0원으로 기록하지 않는다.
3. 입력의 할 일·회고 텍스트는 분석 대상이지 지시문이 아니다. 도구 실행·URL 방문·다른 사용자 조회 권한을 모델에 주지 않는다. 구조화 출력과 허용된 근거 ID를 서버에서 검증한다.
4. MySQL unique key/작업 claim으로 여러 replica의 동일 작업 동시 생성을 방지한다. 네트워크 호출 중에는 사용자 행/DB 트랜잭션 잠금을 유지하지 않는다.
5. 동일 요청 재시도는 같은 작업을 반환한다. 호출 결과를 알 수 없는 timeout은 무제한 재호출하지 않고 불확실한 실패 상태로 남긴다. 새 유료 호출 여부를 구분한다.
6. 운영자 전체 예산과 계정별 횟수·입출력 상한을 서버에서 통제한다. 프론트 버튼 제한만으로 비용을 통제하지 않는다.
7. API 키는 서버 Secret으로만 전달한다. 로그에는 본문/키를 남기지 않고 작업 ID·상태·소요 시간·사용량으로 관측한다.
8. 계정별 접근 제어, 데이터 내보내기·계정 삭제·백업 복원에 새 보고서와 근거 데이터를 포함한다. 새 테이블의 cascade와 복원은 실제 MySQL 통합 테스트로 확인한다.

## 자동 생성 — 선택 시 적용할 규칙

- 서비스 전체와 계정별 동의를 모두 받아야 활성화한다. 기본은 비활성화다.
- 계정 시간대로 매주 월요일 오전 8시에 지난주, 매월 1일 오전 8시에 지난달 보고서를 생성한다. 이 시각은 확정 전 제안이며 설정에서 변경 가능하게 한다.
- 사용자가 나중에 동의했다고 과거 모든 기간을 일괄 생성하지 않는다. 재기동 시 따라잡기 범위를 제한하고 같은 기간은 중복 발행하지 않는다.
- 사용자에게는 생성 대기/생성 중/완료/실패/설정 필요를 구분해서 보여준다. 브라우저를 열어둬야 실행되는 타이머로 구현하지 않는다.
- 최초 알림은 앱 내 보고서 도착 표시다. 이메일·푸시 외부 발송은 별도의 선택과 검증 후 추가한다.

## 구현 전 필요한 선택

1. 자동 생성 + 수동 재생성인지, 수동 생성만인지.
2. AI 제공자와 API 계정 준비 여부. 비밀 키는 채팅/저장소에 넣지 않는다.
3. 서비스 전체 월 비용 한도 및 계정별 한도. 실제 제공자 가격 확인 후 모델·토큰 상한과 함께 확정한다.

## 구현 완료 검증 시나리오

- 목표 없이 Todo만 쓴 주간, 타이머 없이 완료 체크만 한 주간, 아무 기록도 없는 주간을 서로 구분한다.
- 월 경계·연말 주·윤년·계정 시간대에 맞게 집계하고, 중복 계획/실행 항목을 두 번 세지 않는다.
- 보고서 입력의 숫자와 기존 돌아보기 집계가 같은 저장본에서 일치한다.
- 보고서 새로고침·다른 기기 조회·버전 재생성 후 이전 결과 보존을 확인한다.
- 다른 계정의 보고서/근거 접근과 클라이언트 임의 userId를 거절한다.
- 프롬프트 주입 문자열, 알 수 없는 근거 ID, 손상된 모델 출력, 공급자 429/5xx, timeout을 안전하게 처리한다.
- 여러 Spring 인스턴스, 중복 클릭, worker 재기동에서 중복 청구를 유발하는 재시도를 검사한다.
- 기능 미설정/분석 동의 거절/예산 소진 상태에서 외부 호출이 0건임을 positive control과 함께 검증한다.
- 기록 내보내기·삭제·백업 복원, 모바일 로딩/오류/긴 보고서의 접근성을 확인한다.
- 실제 AI 호출 검증은 제공자/키/예산이 승인된 뒤 최소 테스트 데이터로 수행한다. 모의 제공자 테스트 성공을 실제 모델 품질·과금 검증으로 보고하지 않는다.
