# 주간·월간 AI 회고 보고서 — 구현 명세

상태: 2026-09-08 백엔드 구현 및 격리 테스트 단계. **실제 AI 제공자 호출·과금·품질 검증은 아직 하지 않았다.** 제공자 키, 승인된 모델, 입력/출력 단가와 월 예산을 모두 설정해야 동작하며 기본은 비활성화다. 아래 설계 중 현재 한계는 마지막 절에 구분한다.

## 사용자에게 제공할 경험

`돌아보기 → 주/월 선택 → AI 보고서 → 근거 확인 → 다음 기간 계획`

- 직접 쓰는 회고와 AI 보고서는 별개로 보관한다. AI가 사용자의 글을 덮어쓰거나 목표·할 일·일정을 자동 수정하지 않는다.
- 주간 보고서는 날짜별 실행을, 월간 보고서는 해당 월에 포함되는 주별 흐름을 정리한다. 월 경계의 주는 그 달에 속한 날짜만 집계한다.
- 목표나 타이머가 없어도 이용할 수 있다. 계획 시간, 기록 시간, 완료한 일, 목표 측정값을 각각 표시하고 임의의 종합 점수로 합치지 않는다.
- 생성한 보고서는 앱 안에서 기간별 목록으로 다시 연다. 최초 범위에 이메일/PDF 발송, 외부 공개 링크는 포함하지 않는다.
- `다시 생성`은 새 버전을 만든다. 이전 결과와 그때 사용한 근거는 남긴다. 생성 시점보다 나중에 수정한 데이터가 옛 보고서에 자동 반영되는 것처럼 보이지 않게 한다.
- 분기·연간 확장은 같은 구조를 재사용하되, 첫 구현과 검증 범위는 주간·월간으로 한다.

## 보고서 구성

| 구역 | 내용 | 근거가 부족할 때 |
| --- | --- | --- |
| 한눈에 보기 | 기간, 데이터 기준 시각, 완료 개수·계획 시간·기록 시간, 핵심 요약 | 무엇이 기록되지 않았는지 표시 |
| 이번 기간에 한 일 | 날짜별/주별 실제 저장된 완료 항목과 실행 기록 | 날짜 없는 과거 완료 항목은 날짜를 추정하지 않음 |
| 잘된 점 | 반복해서 실행한 행동, 직접 작성한 긍정적 회고 | 기록이 뒷받침하지 않으면 판단 보류 |
| 막힌 점 | 저장된 미완료 일정과 사용자가 적은 방해 요인 | 미완료 이유·감정·건강·생산성을 단정하지 않음 |
| 목표 점검 | 기간에 해당하는 목표와 측정 시점 | 현재값을 과거 기간 말의 값으로 소개하지 않음 |
| 다음 기간 제안 | 근거가 있는 작은 조정 1~3개와 확인 질문 | 성격 평가나 과도한 목표 제안 금지 |

사실 요약과 AI의 해석·제안을 시각적으로 구분한다. 각 관찰에는 근거 항목을 붙인다. 기간 비교는 같은 집계 규칙을 사용하며, 이전 기간에 기록이 없으면 감소율을 계산하지 않는다. 월간 보고서는 주간 AI 결과를 그대로 재요약하지 않고 원본 저장 기록을 바탕으로 작성한다.

## 입력 데이터와 데이터 부족 정책

- JWT로 확인한 본인 계정의 **서버에 저장된** 활성 계획 및 종료·보관 계획, 기간별 목표·회고만 읽는다. 미저장 초안이나 충돌 중인 기기 데이터를 자동 전송하지 않는다.
- 기존 `summarizePeriod` 정책과 일치하게 안정적 항목 ID로 중복을 제거하고, 현재 계획을 우선한다. 계획 시간은 날짜별 구간 합집합으로 계산한다.
- 외부 캘린더의 제목·참석자, 계정 이메일·인증 토큰·연동 비밀값은 전송하지 않는다. 할 일/목표의 자유 메모는 기본 제외하고, 회고 본문은 별도 동의한 분석 범위로 취급한다.
- TimeEntry는 observedAt 기준의 기록 시간이다. 실제 시작/종료 구간이나 자정 너머 실행을 재구성하지 않는다.
- 목표 변화는 비교 가능한 시점의 측정 기록이 있을 때만 서술한다. 현재 목표값과 과거 회고의 최초 checkpoint는 측정 시점이 다를 수 있다.
- 숫자 집계는 서버의 결정적 코드가 수행한다. LLM에 계산을 맡기지 않는다. 입력 크기를 제한할 때 누락 범위를 명시하고 전체 기록을 분석했다고 주장하지 않는다.
- 실행/회고 근거가 전혀 없으면 유료 호출 없이 `보고서를 만들 기록이 아직 없어요`를 반환한다. 템플릿 문장을 AI 결과로 위장하지 않는다.

## 생성과 운영 구조

`사용자 요청 또는 동의된 주기 → 서버 근거 스냅샷 → MySQL 생성 작업 → Spring worker → AI 제공자 → 결과 검증·영속 저장 → 앱에서 조회`

1. 보고서 ID를 AI 호출 전에 발급하고 계정·기간·입력 해시·프롬프트 버전·모델과 함께 저장한다.
2. 본문, 근거 참조, 생성 상태, 생성 시각, 실제 사용 토큰, 비용 계산 근거를 저장한다. 가격 미설정/사용량 미수신은 0원으로 기록하지 않는다.
3. 입력의 할 일·회고 텍스트는 분석 대상이지 지시문이 아니다. 도구 실행·URL 방문·다른 사용자 조회 권한을 모델에 주지 않는다. 구조화 출력과 허용된 근거 ID를 서버에서 검증한다.
4. MySQL unique key/작업 claim으로 여러 replica의 동일 작업 동시 생성을 방지한다. 네트워크 호출 중에는 사용자 행/DB 트랜잭션 잠금을 유지하지 않는다.
5. 동일 요청 재시도는 같은 작업을 반환한다. 호출 결과를 알 수 없는 timeout은 무제한 재호출하지 않고 불확실한 실패 상태로 남긴다. 새 유료 호출 여부를 구분한다.
6. 운영자 전체 예산과 계정별 횟수·입출력 상한을 서버에서 통제한다. 프론트 버튼 제한만으로 비용을 통제하지 않는다.
7. API 키는 서버 Secret으로만 전달한다. 로그에는 본문/키를 남기지 않고 작업 ID·상태·소요 시간·사용량으로 관측한다.
8. 계정별 접근 제어, 데이터 내보내기·계정 삭제·백업 복원에 새 보고서와 근거 데이터를 포함한다. 새 테이블의 cascade와 복원은 실제 MySQL 통합 테스트로 확인한다.

## 자동 생성 — 구현 규칙

- 서비스 전체와 계정별 동의를 모두 받아야 활성화한다. 기본은 비활성화다.
- 계정 시간대로 매주 월요일 오전 8시에 지난주, 매월 1일 오전 8시에 지난달 보고서를 생성한다. 08:00은 기본값이며 설정에서 변경한다. 설정 시각이 지난 뒤 동의하면 바로 따라잡지 않고 다음 해당 주기를 기다린다.
- 사용자가 나중에 동의했다고 과거 모든 기간을 일괄 생성하지 않는다. 재기동 시 따라잡기 범위를 제한하고 같은 기간은 중복 발행하지 않는다.
- 사용자에게는 생성 대기/생성 중/완료/실패/설정 필요를 구분해서 보여준다. 브라우저를 열어둬야 실행되는 타이머로 구현하지 않는다.
- 최초 알림은 앱 내 보고서 도착 표시다. 이메일·푸시 외부 발송은 별도의 선택과 검증 후 추가한다.

## 운영 활성화 전 필요한 선택

1. 자동 생성 + 수동 재생성인지, 수동 생성만인지.
2. AI 제공자와 API 계정 준비 여부. 비밀 키는 채팅/저장소에 넣지 않는다.
3. 서비스 전체 월 비용 한도 및 계정별 한도. 실제 제공자 가격 확인 후 모델·토큰 상한과 함께 확정한다.

## 현재 구현한 API와 저장 구조

모든 API는 로그인한 JWT의 본인 계정만 읽는다. 클라이언트 `userId`는 받지 않는다. 응답은 `Cache-Control: no-store`다.

| API | 동작 |
| --- | --- |
| `GET /api/v1/ai-reviews/config` | 설정 가능 여부, 제공자/모델, 동의·자동 생성 설정과 계정 월 횟수 한도 |
| `PUT /api/v1/ai-reviews/settings` | `consent`, `includeReflections`, `weeklyEnabled`, `monthlyEnabled`, `scheduledTime` 저장. 최초는 모두 false, 시각은 08:00 |
| `POST /api/v1/ai-reviews/reports` | `period: week 또는 month`, `startDate`, `requestId: UUID`. 완료된 주/월에 대한 작업을 예약해 202 반환 |
| `GET /api/v1/ai-reviews/reports?period=week&startDate=YYYY-MM-DD` | 최신순 최대 100개 버전 목록. 필터는 선택 |
| `GET /api/v1/ai-reviews/reports/{id}` | 본인 보고서·고정 근거 조회, 타 계정/없는 ID는 404 |

같은 요청 번호 재전송은 같은 보고서를 돌려주고, 같은 번호로 다른 기간을 보내면 409다. 응답을 못 받았다고 새 번호로 자동 재요청하지 않는다. DTO의 `requestId`로 목록에서 대조한다. 사용자가 명시적으로 새 버전을 만들 때만 새 번호를 사용한다.

상태는 `QUEUED → RUNNING → READY / FAILED / UNKNOWN / CANCELLED`이다. 네트워크 결과가 불명확하거나 워커가 중간에 죽으면 `UNKNOWN`으로 남기고 자동 재호출하지 않는다. `RUNNING`이 5분 이상 이어지면 동일 정책으로 회수한다. 사용자는 운영자 확인 없이 불명확한 요청을 유료 재시도하지 않는 것이 안전하다.

AI 동의 철회는 설정 변경과 같은 트랜잭션에서 **아직 외부 전송을 시작하지 않은** 대기/claim 작업을 `CANCELLED`로 고정하고 예약 금액을 환불한다. 회고 본문 포함 동의만 철회하면 회고 근거가 포함된 미전송 작업만 취소한다. 다시 동의해도 이전 요청은 살아나지 않으며 새 보고서는 새 명시적 요청이 필요하다.

동의 확인·전송 승인(`provider_started_at`)은 settings→report 잠금 순서로 직렬화하고 네트워크 호출 전 커밋한다. 철회가 먼저면 전송할 수 없고, 전송 승인이 먼저면 이미 시작한 외부 처리로 보아 회수/무상 환불을 보장하지 않는다. 실제 HTTP 동안 DB 잠금은 유지하지 않는다.

Flyway V14 테이블:

- `ai_review_setting`: 계정별 동의, 회고 본문 포함 선택, 주간/월간 자동 생성과 시각.
- `ai_review_report`: 보고서 ID/요청 ID/버전, 당시 근거 JSON/해시/프롬프트 버전/모델, 상태/검증된 결과, 사용량/비용. 계정 삭제 시 cascade.
- `ai_review_budget_month`: UTC 월별 전체 예약·확정 비용. 개인정보 없는 합계이며 계정 삭제로 예산이 되살아나지 않게 유지한다.

월별 예산 행 잠금 안에서 중복 요청, 계정 월 횟수, 최대 토큰 비용 예약과 버전을 결정한다. 워커 claim은 `FOR UPDATE SKIP LOCKED`이고 **트랜잭션을 종료한 뒤** 제공자에게 요청한다. 알려진 사용량은 설정 단가로 정산하고, 누락/불확실한 사용량은 `usage/costUsd = null`로 남기며 최대 예약분을 유지한다. 0원으로 위장하지 않는다. 실제 공급자 과금은 운영자가 고지한 단가와 일치하는지 별도 대조해야 한다.

## 운영자 활성화 설정

다음 값은 서버 환경 변수/Secret으로만 주입한다. 예시 키나 임의 모델·가격을 기본으로 넣지 않는다.

| 환경 변수 | 초기값 / 의미 |
| --- | --- |
| `NOWLINE_AI_ENABLED` | false; 운영자 검증 후 true |
| `NOWLINE_AI_API_KEY` | 빈 값; 서버 Secret |
| `NOWLINE_AI_MODEL` | 빈 값; 승인한 Structured Outputs 지원 모델 |
| `NOWLINE_AI_MONTHLY_BUDGET_USD` | 0; UTC 월별 전체 서비스 비용 한도 |
| `NOWLINE_AI_INPUT_PRICE_PER_MILLION` | 0; 승인 모델의 입력 100만 토큰당 USD |
| `NOWLINE_AI_OUTPUT_PRICE_PER_MILLION` | 0; 출력 100만 토큰당 USD |
| `NOWLINE_AI_MONTHLY_REPORT_LIMIT` | 8; 계정별 한 달 작업 수(실패/불확실한 호출 포함) |
| `NOWLINE_AI_MAX_INPUT_BYTES` | 32768; 초과하면 조용히 잘라 보내지 않고 422 |
| `NOWLINE_AI_MAX_OUTPUT_TOKENS` | 1600; 응답 토큰 상한 |

현재 어댑터는 OpenAI Responses API만 지원하며 임의 endpoint를 받지 않는다. `store:false`, `text.format`의 strict JSON schema, 도구 없음, 60초 요청 제한을 사용한다. 반환된 근거 ID와 필드/길이를 다시 서버에서 검사한다. 구조화 출력은 사실 정확성 보장이 아니며 모델 평가가 별도로 필요하다. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [Responses 요청 명세](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

`store:false`만으로 제공자의 모든 로그 보관이 사라진다고 안내하지 않는다. 운영자는 활성화 전에 자신의 API 프로젝트 데이터 처리/보관 조건을 확인하고 실제 개인정보 안내에 반영해야 한다.

## 현재 구현 범위와 남은 외부 게이트

- 주/월은 완료된 기간만 생성한다. 주간은 월요일, 월간은 매월 1일에 사용자 설정 시각부터 최대 2시간 동안 직전 기간 하나만 예약한다. 사용자가 명시적으로 자동 생성을 켜야 하고 과거 전체 기간을 따라잡지 않는다. 보고서 도착 이메일/푸시는 이번 범위에 없다.
- 자동 생성과 수동 생성은 같은 서버 집계와 예산 정책을 사용한다. 월간은 원본 기록을 사용하며 주간 AI 결과를 재요약하지 않는다.
- 현재 계획 우선, 종료/보관 계획은 최신 저장 순서로 안정적 항목 ID 중복을 제거한다. 외부 일정/할 일 자유 메모/실행 근거 메모/계정 이메일은 보내지 않는다. 사용자 회고 본문은 별도 동의한 경우만 포함한다.
- 숫자는 완료일이 있는 완료 작업 수, 날짜별 계획 구간의 합집합 분, observedAt 날짜의 기록 초를 구분한다. 날짜 없는 완료·실제 시작/종료 구간은 복원하지 않는다.
- 기간 목표는 생성 시점의 현재 값임을 표시한다. 과거 기간말 값이나 과거 대비 변화율, legacy outcome의 변경 이력을 추정하지 않는다. 현재 버전은 자동 비교 분석 대신 근거 있는 관찰과 다음 제안을 제공한다.
- 입력 한도 초과는 422로 중단한다. 보관 계획·기간 문서 원본 합계가 2 MiB를 넘으면 메모리 보호를 위해 먼저 중단하며, 이 경우 작은 기간 선택만으로 해결된다고 보장하지 않는다. 부분만 읽고 “전체 분석 완료”라고 쓰지 않는다. 큰 계정의 서버 측 기간 쿼리 최적화는 후속 확장 항목이다.
- 계정 내보내기에 AI 설정/모든 버전/근거를 포함하며 삭제 FK를 격리 MySQL에서 검증한다. 운영 백업 복원 연습은 별도 운영 게이트다.
- 실제 API 프로젝트와 모델/예산 승인 후 최소한의 테스트 데이터로 정상 응답, refusal, 토큰 사용량/청구 대조, 한국어 품질과 프롬프트 주입 방어를 확인해야 한다. 미승인 상태에서 개인 일정·회고를 전송하지 않았다.

## 구현 완료 검증 시나리오

- 목표 없이 Todo만 쓴 주간, 타이머 없이 완료 체크만 한 주간, 아무 기록도 없는 주간을 서로 구분한다.
- 월 경계·연말 주·윤년·계정 시간대에 맞게 집계하고, 중복 계획/실행 항목을 두 번 세지 않는다.
- 보고서 입력의 숫자와 기존 돌아보기 집계가 같은 저장본에서 일치한다.
- 보고서 새로고침·다른 기기 조회·버전 재생성 후 이전 결과 보존을 확인한다.
- 다른 계정의 보고서/근거 접근과 클라이언트 임의 userId를 거절한다.
- 프롬프트 주입 문자열, 알 수 없는 근거 ID, 손상된 모델 출력, 공급자 429/5xx, timeout을 안전하게 처리한다.
- 여러 Spring 인스턴스, 중복 클릭, worker 재기동에서 중복 청구를 유발하는 재시도를 검사한다.
- 기능 미설정/분석 동의 거절/예산 소진 상태에서 외부 호출이 0건임을 positive control과 함께 검증한다.
- 기록 내보내기·삭제·백업 복원, 모바일 로딩/오류/긴 보고서의 접근성을 확인한다.
- 실제 AI 호출 검증은 제공자/키/예산이 승인된 뒤 최소 테스트 데이터로 수행한다. 모의 제공자 테스트 성공을 실제 모델 품질·과금 검증으로 보고하지 않는다.
