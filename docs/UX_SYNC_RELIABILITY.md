# 할 일 중심 사용성 및 동기화 개선

## 확인된 원인

기존 Today는 시간표를 먼저 보여주고 휴대폰의 할 일 입력을 별도 팝업에 숨겼다. 시간 배치된 항목이 할 일 목록에서 사라져 동일한 항목인지 이해하기 어려웠다. 기기 갱신은 주로 시작/재접속에 의존해 이미 열려 있는 다른 화면이 오래된 상태를 유지했다. 전체 스냅샷 충돌은 항목이 달라도 수동 해결이 필요했다.

브라우저 재현 중에는 “목표 없이 시작”이 내부 계획의 필수 문자열을 비워 서버가 400으로 거절하는 별도 문제도 확인했다. 내부 기본 이름을 유효한 값으로 저장하고 기존 빈 로컬 문자열도 정상화한다. 사용자 목표나 예제 할 일을 만들어 넣지 않는다.

## 사용자 규칙

- 할 일은 하나의 ID다. 시간 배치는 같은 ID를 가리키며 목록과 시간표에 함께 표시된다.
- `plannedDate`는 날짜만 있는 할 일을 지원한다. 없거나 `later`이고 시간 블록도 없는 항목은 나중에 목록이다. 기존 날짜 없는 항목/블록은 호환된다.
- 한 할 일에 여러 블록을 유지할 수 있다. 날짜 변경은 선택한 날짜의 연결 블록들을 같은 시각/길이로 함께 옮긴다. 목적지와 겹치면 전체 이동을 거절한다.
- 나중에 보내기는 선택한 날짜의 계획 블록만 해제한다. 다른 날짜의 블록과 실제 시간 기록은 유지한다.
- 체크는 타이머 없이 완료/취소 가능하다. 실행 중인 타이머는 기존 종료·기록 흐름을 따른다. 계획 시간과 실행 기록은 별개다.
- 모바일의 할 일/시간표 탭은 작성 중 입력과 스크롤 상태를 보존한다.

## 저장과 동시 수정

서버의 strong ETag/revision/멱등성 키를 유지한다. 열린 화면은 보이는 동안 1초 간격의 조건부 GET으로 확인하고 탭 복귀/재접속 시 즉시 갱신한다. 숨겨진/오프라인/충돌 화면은 polling을 중단하고 중복 요청을 막는다. 일시적 실패는 1–30초 간격으로 재시도한다.

서버에 마지막으로 확인받은 공통 상태를 기준으로 ID·필드 단위 3-way merge를 수행한다. 다른 항목/필드의 변경은 보존하고 같은 필드만 충돌로 보여준다. 연결 블록 제목은 할 일의 제목을 따른다. 하위 항목의 체크와 순서 변경도 병합한다. 타이머, 시간 범위, 완료 상태는 분리해 섞지 않는다. 병합으로 생긴 시간 겹침이나 삭제된 ID 참조는 자동 저장하지 않는다.

진짜 충돌은 이 기기/서버/기준 원본을 계정별 로컬 백업으로 보존하고 명시적 항목 선택이 필요하다. 비교 화면의 선택은 해당 필드에만 적용되며 독립 변경을 덮어쓰지 않는다. 전체 원본 선택은 별도의 명시적 복구 경로다. 다른 기기에서 종료/삭제한 계획은 오래된 캐시에서 자동 부활시키지 않는다.

편집창에서는 수정한 필드만 저장한다. 편집 중 동일 필드가 원격으로 바뀌면 입력을 보존하고 알린다. 시간만 바꾸는 저장은 다른 기기의 최신 제목/메모를 되돌리지 않는다.

기존 스냅샷 API를 유지한 이유는 인증·revision·서버 검증·모바일 호환성을 보존하면서 현재 문제를 해결하기 위해서다. SSE/WebSocket이나 operation 기반 부분 API는 다수 사용자 운영 부하 측정 후 별도 검토 대상이다. 1초 polling이 모든 네트워크/백그라운드 환경의 2초 반영을 보장하는 것은 아니다.

## 검증

- 프론트엔드 전체 테스트, production build 및 Capacitor sync.
- Spring/MySQL 통합 테스트: plannedDate round-trip, 실제 날짜 검증, 옛 클라이언트의 날짜 유실 방지, export.
- Provider 두 인스턴스: 실시간 갱신, 동시 수정, 오프라인/포커스, 삭제/수정 경합, 서버 계획 종료, 여러 블록 날짜 이동 및 실제 기록 보존.
- `scripts/lib/planner-sync-journey.mjs`: 독립 desktop/mobile 브라우저 세션에서 생성·시간 변경·완료·취소·동시 추가·오프라인 실제 충돌·필드 선택·reload·삭제/수정·날짜 이동을 검증한다. localhost의 폐기 가능한 테스트 스택에만 실행한다. `npm run verify:production:e2e`에 포함되어 CI에서도 실행된다.
- 실제 브라우저에서 5단계 과업을 완료했고 320/390px 긴 제목 및 시간 편집을 확인했다. 새 테스트 스택의 최초 측정 5회는 1314 / 1058 / 565 / 1330 / 817ms였다. 운영 인터넷/실물 휴대폰 측정값은 아니다.
- 시각적 비교와 제한은 루트 `design-qa.md` 참고.

별도 `verify:production:contracts`의 App Store 키 이름 검사에는 기존 main에서도 동일한 불일치가 있다. 이번 웹 CI/배포 경로의 검사 항목은 아니며, 모바일 스토어 배포 설정을 임의로 변경하지 않았다. MySQL contract 검사는 통과했다.

## 5분 사용자 확인표 — 아직 실제 신규 사용자 검증 아님

설명을 먼저 읽지 않은 사람에게 아래 과업 이름만 제시한다. 각 첫 시도에 성공 여부, 시간, 클릭/터치 수, 멈춘 곳과 예상과 달랐던 상태를 기록한다.

| 과업 | 성공 기준 | 결과 기록 |
|---|---|---|
| 오늘 “개인 공부” 등록 | 바로 보이는 입력으로 등록, 오늘 목록에 표시 | 성공 / 초 / 터치 수 / 멈춤 |
| 오후 6–8시로 지정 | 같은 할 일이 18–20시 목록·시간표에 표시 | 성공 / 초 / 터치 수 / 멈춤 |
| 오후 7–9시로 변경 | 중복 없이 기존 시간이 19–21시로 변경 | 성공 / 초 / 터치 수 / 멈춤 |
| 내일로 미루기 | 오늘에서 빠지고 내일 19–21시에 표시 | 성공 / 초 / 터치 수 / 멈춤 |
| 완료 후 취소 | 체크 후 취소할 수 있고 같은 항목이 복구 | 성공 / 초 / 터치 수 / 멈춤 |

휴대폰과 컴퓨터를 함께 열어 동일 계정의 반영 속도도 확인한다. 실패/멈춤 지점을 다음 UX 수정 근거로 사용한다. 코드 테스트 통과를 인간의 직관성 검증 결과로 대신하지 않는다.

## 배포 안전성

`V16__add_task_planned_date.sql`은 nullable 컬럼 추가만 수행한다. 기존 DB/PVC를 초기화하지 않는다. 기존 main 자동 배포는 CI → immutable SHA/digest → Mac mini DB 백업 → rollout → 공개 revision 검증 경로를 사용한다. 관련 사용자 로컬 변경과 서버의 운영 스크립트 변경은 보존한다. 운영 데이터는 테스트용으로 수정하지 않는다.
